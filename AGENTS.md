# Lion Engine Agent Guide

Lion is a 2D game engine written in C++20.

## Project identity

A folder is never named after its Visual Studio project, so a path always distinguishes the source
area from the build target:

| Folder | VS project | Group | Output | Responsibility |
|---|---|---|---|---|
| `Engine/` | `Lion` | Core | `lion-core.dll` | Engine runtime and public API |
| `Sandbox/` | `Game` | Runtime | `lion-game.dll` | Built-in Brickout module; components live in `Sandbox/Assets/Scripts/` |
| `Editor/` | `Mane` | Tools | `Lion.exe` | Lion editor |
| `Launcher/` | `Launcher` | Tools | `lion-launcher.exe` | Thin standalone launcher; owns no game behavior |

Module filenames are fixed in `Lion/Core/GameModule.h`, not derived from a project name. Loaders must
not care what a game calls itself. `lion-game.loaded.dll` is the editor's private hot-reload copy.

## Communication and language

- Speak Portuguese with the user.
- Write code, identifiers, comments, documentation, commit messages, and PR text in English.

## Git delivery

- Work on `dev`. Always commit verified work and push it to `origin/dev`; never merge or modify `main`.
  The user opens and merges the PR.
- Bump `kVersion` in `Engine/Source/Lion/Core/Version.h` before committing: patch for a fix, minor for a
  new capability, and major for behavior that breaks games written against the earlier version. The
  editor status bar reads this value.
- Only commit what was verified working. Visual or behavioral changes must be run and inspected; a
  successful compilation does not verify behavior.
- Preserve unrelated and user-created working-tree changes. Stage only files belonging to the request.
- Project-authored content is not the engine. Do not modify scripts generated by the editor unless the
  user asks. The repository-owned Brickout components are the exception because the Sandbox demo is part
  of this repository.

## Design principles

Apply these to every change:

- Clean Code: names state intent, functions stay focused, and behavior is unsurprising.
- KISS and YAGNI: implement the smallest complete solution and avoid speculative frameworks.
- DRY: keep every rule in one source of truth. Shortcut handling, for example, belongs in the shared
  shortcut path rather than being reimplemented by individual panels or the viewport.
- SOLID: depend on abstractions at module boundaries. `Component::Serialize` takes an abstract
  `Serializer` so JSON types never cross a component translation unit or DLL boundary.
- Treat performance as a feature. Pass by `const&`, reserve stable buffers, avoid per-frame allocation
  and repeated filesystem traversal, and clip long rendered lists.

## C++ conventions

- Types and functions use `PascalCase`; locals and parameters use `camelCase`; members use `mCamelCase`;
  constants use `kPascalCase`; macros use `LION_UPPER_CASE`.
- Use Allman braces and tabs. A minority of older files are space-indented; match the file instead of
  reformatting it. Omit braces for a single-statement `if` when that matches the surrounding code.
- Use Lion aliases: `int32`, `float32`, `char8`, `Scope<T>`, `Reference<T>`, `MakeScope`, and
  `MakeReference`.
- Headers use `#pragma once`. Public engine headers export with `LION_API`, avoid third-party types, and
  forward-declare where practical.
- Comments explain constraints, tradeoffs, and reasons, never restate what the code does or address a
  reviewer. Public documentation follows the Google C++ doc-comment style.

## Architecture boundaries

- Entities are composed, never subclassed. `Entity` is final: a name, a `Transform`, and attached
  components. Gameplay and collision behavior belong in `Component` subclasses. A component needing
  another trait asks its owner or scene rather than depending on an entity subtype.
- Components register with `LION_REGISTER_COMPONENT`; registration names are the scene/editor ABI.
- Describe editable component fields once through `Reflect()`. Reflection drives Inspector widgets and
  scene serialization through abstract `Reflector`/`Serializer` boundaries.
- C++ source generation stops at `Editor/Source/ComponentScripts`. Scenes, reflection, the Inspector, and
  the registry speak stable component names and fields, not implementation languages. Add a later C#
  backend at this boundary rather than branching the entity/component model.
- The game is a dynamically loaded module. Loading runs component static registration. Keep component
  factories and live instances from surviving module unload.
- Hot reload serializes the scene, drops registry factories and live components, unloads the private DLL
  copy, loads the rebuilt module, and deserializes. Nothing may retain a `Reference<Entity>` whose
  component vtable points into the unloaded module.
- Keep engine, game module, editor, and launcher responsibilities separate. The launcher owns no game
  behavior.
- The editor and game module share one `lion-core.dll` and the `/MD` runtime. This makes registry state
  visible across modules and cross-module allocation safe.
- A project owns its generated game-module build, Unreal-style. The editor regenerates
  `<project>/Build/lion-game.vcxproj` and the project-root solution before compilation. Distributed
  projects compile against the packaged `Include/` tree and `Bin/lion-core.lib` assembled by
  `Scripts/PackSdk.bat`; only the built-in Sandbox builds through `Lion.sln`.
- `%{wks.location}` becomes `$(SolutionDir)`. Building a generated `.vcxproj` directly therefore breaks
  paths that depend on the solution. Build through the solution.
- The Sandbox is scene-authored. `Sandbox/Assets/Scenes/Level01.lnscene` through `Level05.lnscene` own
  the five Brickout levels; `GameLayer` enters through Level01 and `SceneManager` performs transitions.
  Gameplay components provide reusable behavior rather than a second code-only level description.

## Centralized engine rules

- Sealing lives only in `Lion/Core/Vault.h`: XOR with `0x07D2`, URL-safe base64, wrapped at 76 characters.
  Loading calls `Vault::Unseal`, which returns unsealed content unchanged. Scenes, input maps and project
  markers are sealed when saved; Shipping seals every packaged game asset, including `.lnshader`, `.lnscene`,
  `.lninput`, images, and audio. Sealing is obfuscation, not encryption, because the key ships with the
  player.
- Module filenames live in `Lion/Core/GameModule.h`.
- Shortcut handling lives in the shared shortcut path.

## Editor, assets, and UI

- Scene and serialized asset paths are resource-relative and use forward slashes. Never save a
  machine-specific absolute asset path.
- Both editor and launcher anchor assets, modules, and editor state to the executable, not the working
  directory.
- Keep UI harmonious across panels, tabs, and modals. Reuse established spacing, alignment, breathing
  room, control order, colors, typography, and interaction patterns before adding a new visual rule.
- Editor icons come from Material Design Icons. `EditorGui::LoadIconFont` loads the font twice: merged at
  16 px for an icon inline with a label, and standalone at 32 px atlas resolution for positioned icons.
- Inline icons use one string and one draw call, such as `ICON_MDI_x "  Label"`. Positioned icons go
  through `DrawIcon(origin, box, glyph, colour, pixels)` and `EditorGui::GetIconFont()` so they remain
  sharp when scaled down.
- Icon sizes are even and follow a 4 px grid. Use `kIconSize` (16) for toolbars, rows, filters, menus,
  tabs, component headers, and row-end widgets; use `kIconTitle` (24) for the single panel heading icon.
  Do not spell ad-hoc sizes at call sites or substitute text placeholders for missing icons.
- When a prototype needs reusable behavior, decide whether it is a general engine API or game-specific
  client behavior. Ask the user when that boundary is genuinely unclear.

## Build system

All repository artifacts land under `Build/`. Each vendored dependency builds under its own
`Vendor/<lib>/Build/` directory. Every dependency is a submodule fork under `github.com/TheSampaio` with
its own `premake5.lua`, so a fresh checkout uses `git clone --recursive`. Licenses for Lion and third
parties are gathered as Markdown under `Licenses/` beside the executables by
`Scripts/PackLicenses.bat`.

From the repository root:

```bat
Scripts\Build.bat Debug
Scripts\Build.bat Release
Scripts\Build.bat Shipping
```

The build graph is declared by project dependencies; the script does not manually order projects.
Post-build steps create their destination directories.

Manual generation and builds:

```bat
premake5 vs2022
MSBuild Lion.sln -p:Configuration=Debug -p:Platform=x64 -m
MSBuild Lion.sln -t:Runtime\Game -p:Configuration=Debug -p:Platform=x64
```

Premake captures globbed file lists at generation time. Regenerate the Visual Studio projects whenever
a C++ file is added or removed. A single-project MSBuild target is `<solution folder>\<project>`;
moving a project between groups renames that target. The editor Compile command builds `Runtime\Game`.

## Configuration behavior and verification

Debug is unoptimized, has symbols, and logs everything. Release is optimized, has no symbols, and game
logging keeps Error/Warning/Success. Shipping is optimized, has no symbols, logs nothing, and uses the
player entry point. The editor is a tool and requests full logging in every configuration at runtime;
do not add call-site `#ifdef` policy around logging in the shared engine DLL.

Before committing:

1. Build Debug, Release, and Shipping.
2. Run `Build/Bin/<config>/Mane/Lion.exe` in all three configurations.
3. Run `Build/Bin/<config>/Launcher/lion-launcher.exe` in all three configurations.
4. Exercise changed behavior and visually inspect editor/UI changes with screenshots.
5. Review `git diff` and stage only requested files.
